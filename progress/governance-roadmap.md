# Log Governance Roadmap

## 1. Purpose

This file is the entry point for a contributor returning to Lumina Studio log governance after one to three months, or for a new maintainer reviewing the first logging-touching PR in this area.
It summarizes the state left by rounds 7 through 16: what the canonical workflow gate covers, which success canaries are load-bearing, where the INFO budget still has headroom, and which user-facing flows remain outside `scripts/log_quality_check.py`.
Read this file first, then read `progress/round-7-10-master-plan.md`, then the per-round prompt files `progress/round-7-prompt.md` through `progress/round-10-prompt.md`, then `progress/round-11-prompt.md`, then `progress/round-12-to-16-prompt.md`, and finally the Logging Governance bullets in `AGENTS.md`.
The roadmap does not create new policy.
It records the current contract so future work can change that contract deliberately, with tests and gate updates, instead of by accident.
The core review question for future logging work is simple: does the PR preserve structured events, preserve the budget, and preserve a canary that proves the user-visible success path completed?
If the answer is not obvious within five minutes, this roadmap should tell the reviewer where to look next.
The most important source files are `scripts/log_quality_check.py`, `tests/test_logging_exception_governance_unit.py`, `api/structured_logging.py`, and `api/logger.py`.
The most important runtime outputs are the `progress/log_audit_*.json` reports generated by the gate runner.
The most important branch protocol is the GPT-5.5 execution agent to Cascade verifier to user oversight chain defined in the master plans.
For day-to-day PR review, do not start by reading every historical PR.
Start with the coverage map and budget table below, then inspect the touched code against those invariants.
If the PR touches logging but not any listed workflow, treat that as a signal to ask whether this roadmap needs a new uncovered-workflow entry or a new governance round.
Round 17 is the first round of the v2 governance program documented in `progress/round-17-onwards-master-plan.md`, which extends coverage to all backend mutating endpoints and culminates in the `log-governance-v2` tag.

`WORKFLOW_ORDER` is currently `startup`, `lut_list`, `lut_colors`, `preview`, `generate`, `vector`, `replace`, `replace_bw`, `replace_8color`, `replace_5color_ext`, `extract`, `merge_8color`, and `merge_5color_ext`.
The default workflow is `startup,lut_list,lut_colors,preview,generate,replace,extract,merge_8color,merge_5color_ext`.
The default workflow consumes INFO `28/30`, with per-endpoint max `7/8`.
The five fire-on-success canaries in the default gate are `converter_region_replace_timing`, `vector_matched_rgb_overrides_applied`, `extractor_extract_done`, `extractor_merge_8color_done`, and `extractor_merge_5color_extended_done`.
The replace family is the set `{replace, replace_bw, replace_8color, replace_5color_ext}`.
Exactly one replace-family member may appear in a single workflow run.
The `vector` step is also mutually exclusive with every replace-family member because the replace path already exercises the vector region-replace branch and because combining both paths would distort the INFO budget.
`EXTRACTOR_STRUCTURED_EVENTS` now contains seven entries: `extract`, `merge_8color`, `merge_5color_extended`, `manual_fix`, `preview_wb`, `rotate`, and `confirm_palette`.
The first three are workflow rows above.
The remaining four are success-path extractor canaries governed by the extractor structured-event inventory and by endpoint-specific gates from rounds 12 through 16.
`_workflow_required_event_checks` currently asserts replace-family canaries and extractor canaries.
In `full` mode, replace-family gates require both `converter_region_replace_timing` and `vector_matched_rgb_overrides_applied`.
In `fast` mode, replace-family gates require `converter_region_replace_timing`; worker-level vector canaries are not expected from the fast-mode mocks.
The `extract`, `merge_8color`, and `merge_5color_ext` steps require their corresponding extractor done canaries in both `fast` and `full` modes.
The `startup`, `lut_list`, `lut_colors`, `preview`, `generate`, and `vector` rows still matter because they keep the gate representative, but their specific event presence is enforced by endpoint success, structured logging governance, and audit review rather than by additional entries in `_workflow_required_event_checks`.
Do not add a second INFO canary to any row unless the workflow's user-visible success path cannot otherwise be proven.
If a new row is added to `WORKFLOW_ORDER`, the default workflow should not change automatically.
Default-gate changes need their own governance round because they change the budget baseline.

The default canonical workflow is `startup,lut_list,lut_colors,preview,generate,replace,extract,merge_8color,merge_5color_ext`.
The 30-line cap on a full startup plus LUT plus preview plus generate plus replace plus extractor run is a deliberate trip-wire.
It keeps the workflow useful as a review signal rather than a noisy transcript.
The cap cannot be raised without an explicit governance round.
The 8-line per-endpoint cap exists so one request-scoped endpoint cannot consume the budget that should be shared across the workflow.
That cap is especially important for the override and region-replace path, which already sits near the limit.
Headroom today is `2/30` for the full default gate, with current usage at `28/30`.
Per-endpoint headroom today is `7/8`, leaving 1 spare INFO line on the override and region-replace endpoint.
The next round-17+ INFO budget should come from demoting another diagnostic or intermediate event, not from raising thresholds.
Likely places to inspect first are `core/pipeline/coordinator.py` and `core/converter/replace.py`.
Use the round 7 pattern: keep the orchestration-level success canary at INFO, and demote implementation detail to DEBUG.
Do not demote `converter_region_replace_timing`, `vector_matched_rgb_overrides_applied`, `extractor_extract_done`, `extractor_merge_8color_done`, or `extractor_merge_5color_extended_done` without replacing their coverage with an equally specific success canary.
Do not count `request_completed` as budget relief.
The catch-all bucket must remain at zero.
The round 9 per-mode alternates are runtime checks, not default-baseline files.
Their current full-mode result remains below the default 9-step gate and per-endpoint max `7/8` for `replace_bw`, `replace_8color`, and `replace_5color_ext`.
If those numbers change, document why in the PR body before asking Cascade to verify.

## 4. Yellow flags

- **Per-endpoint headroom is 1 slot.**
  The override and region-replace endpoint sits at `7/8`.
  Adding any new INFO emission on that endpoint will trip the cap.
  Round 17+ work touching this endpoint should find a DEBUG demotion candidate before adding another INFO line.

- **Synthetic-fixture fallback policy.**
  Round 8 uses an in-memory `100x100` grid PNG for the extractor workflow.
  Round 9 uses real on-disk LUT presets under `lut-preset/`.
  Neither round added on-disk fixtures.
  Future rounds touching new endpoints should prefer this order: real preset, in-memory synthesis, on-disk fixture.
  The on-disk fixture option should be the last resort and should be called out for Reviewer approval.

- **Reusable helpers added in round 12-16.**
  `_synthesize_lut_keyed_json` and `_synthesize_rgb_png_bytes` in `scripts/log_quality_check.py` are the canonical fixture builders for round 17+ workflow steps.
  New rounds should reuse them rather than re-synthesize.

- **Default canonical now 9-step.**
  Round 12 added `merge_5color_ext`.
  The next default-canonical change is anticipated in round 17+ PR #112 when single-stage extract joins the canonical.

- **BW canary list.**
  `replace_bw` fires both `converter_region_replace_timing` and `vector_matched_rgb_overrides_applied` today.
  If a future BW-focused refactor changes the override branch entry condition, this assumption may break.
  Watch for `vector_matched_rgb_overrides_applied` regressions in BW-specific PRs.
  If the branch legitimately no longer runs for BW, reduce BW's required canary list explicitly instead of adding a fake event.

- **Per-mode baselines deferred.**
  Round 9 chose Option B.
  No per-mode reviewer baseline files were committed.
  `replace_bw`, `replace_8color`, and `replace_5color_ext` are runtime-only checks.
  If per-mode regressions become recurring, escalate to Option A in a follow-up governance round.

- **Fast-mode and full-mode canary expectations differ.**
  Fast mode uses mocks and does not prove worker-level vector canaries.
  Full mode is the source of truth for `vector_matched_rgb_overrides_applied`.
  A fast-mode pass is useful for script shape and API wiring, not for the full override branch.

- **Async status remains under-covered.**
  The replace-family gate waits for async GLB status to settle, but async status and progress polling are not first-class workflow rows.
  Treat regressions around `glb-status` as candidates for a future workflow step rather than expanding the v1 document.

- **Generated audit files are easy to leak into a PR.**
  `scripts/log_quality_check.py` writes timestamped files under `progress/`.
  Round 17's diff must remain one changed file.
  Future rounds that regenerate baselines should commit only intentional baseline files and leave timestamped scratch output untracked.

## 6. Threshold review schedule

`DEFAULT_MAX_INFO = 30` in `scripts/log_quality_check.py`.
`DEFAULT_MAX_INFO_PER_ENDPOINT = 8` in `scripts/log_quality_check.py`.
These are not to be raised as a fix for failing gates.
A failing gate means the PR needs a root-cause analysis: duplicated INFO, a new canary that should be DEBUG, a workflow change that needs a new baseline, or a legitimate governance round.
Baseline regeneration should happen only when the default canonical workflow legitimately changes its INFO line count from the current `28/30`.
Timestamped ad-hoc audit output should not be committed as a substitute for an intentional baseline update.
Every governance round should add a new roadmap entry or append a delta note to this file.
If six months pass without a governance round and any logging-touching PR has landed, the next reviewer should re-audit `scripts/log_quality_check.py`, `tests/test_logging_exception_governance_unit.py`, and the latest `progress/log_audit_*.json` files before approving another logging change.
The review should check `WORKFLOW_ORDER`, `_workflow_required_event_checks`, the structured-event allowlists, the default workflow, and the budget numbers.
If a single legitimate canary change appears to force a cap raise, surface that to the user.
Do not raise the cap unilaterally.
Prefer a round-level decision that names the canary, explains why it must be INFO, and identifies any event that can be demoted to keep the budget stable.
If the cap must still change after that analysis, the PR body should say so explicitly and Cascade should verify the full gate under the new policy.
Rollback remains available through a normal revert of the offending governance PR.
The rollback should restore the prior script behavior and the prior documented numbers together.
Round 17+ PRs may temporarily approach 30/30; PR #116 will demote one diagnostic event to DEBUG to free a slot if needed. Tag `log-governance-v2` is cut after PR #116 lands.

## 7. Subagent SDD pattern

The current authority document for rounds 7 through 16, extended in rounds 17-62, starts with `progress/round-7-10-master-plan.md`.
The v1 per-round prompts are `progress/round-7-prompt.md`, `progress/round-8-prompt.md`, `progress/round-9-prompt.md`, `progress/round-10-prompt.md`, `progress/round-11-prompt.md`, and `progress/round-12-to-16-prompt.md`.
The protocol is GPT-5.5 for execution, Cascade for verification and merge, and the user for oversight and final acceptance.
GPT-5.5 may branch, edit, test, commit, push, and open the PR.
GPT-5.5 must not merge the PR.
Cascade verifies against the master plan gates and either merges or rejects.
The cross-round handoff templates live in master plan §4.
Use those templates for kick-off, draft status, handoff, rejection, and acceptance messages.
The six roles per round are Investigator, Implementer, Test Author, Verifier, Reviewer, and PR Author.
Their responsibilities are defined in master plan §3.
Round 10 is unusual because Test Author performs a no-test confirmation rather than writing tests.
Round 17 onwards follows the same six-role pattern but is documented per-PR in `progress/round-17-onwards-master-plan.md`.
Each PR's mega-prompt at `progress/round-NN-prompt.md` is written by Cascade after the previous PR has merged, so the prompt always references real merged-state facts.
`progress/round-7-prompt.md` is the simplest example because it changes one event level and one budget line.
For larger rounds, keep the same shape but narrow each role's ownership and verification table.
The pattern works only if each PR remains a single concern.
If the round uncovers an unrelated defect, record it in the PR body or a follow-up issue and do not fix it in the same PR unless the verifier rejects the round because of it.

## 8. Glossary

**Canary event**: a single INFO log line whose presence proves the success path completed.
Canaries are asserted by `_workflow_required_event_checks` in `scripts/log_quality_check.py` for replace-family and extractor workflows.

**Governance**: the policy that production INFO emissions are structured, named, budgeted, and gated by a workflow runner.
The source of this policy is the Logging Governance section in `AGENTS.md`.

**Structured event**: a log record carrying `extra={"event": "<snake_case_name>", ...}` with actionable fields beyond the message string.
The structured-event inventory is asserted by `tests/test_logging_exception_governance_unit.py`.

**`request_id` / `session_id`**: opaque correlation identifiers.
`request_id` is per HTTP request.
`session_id` is per extractor or conversion session.
Both should appear in warning and error records on request paths when the context exists.

**Workflow gate**: one end-to-end run of `scripts/log_quality_check.py` with a specific workflow step list.
The default PR-time gate is `startup,lut_list,lut_colors,preview,generate,replace,extract,merge_8color,merge_5color_ext`.

**Replace family**: the four sibling steps `{replace, replace_bw, replace_8color, replace_5color_ext}`.
They are mutually exclusive within a single workflow run.

**Default baseline**: the expected INFO count and per-endpoint maximum for the default workflow.
After round 16, that baseline is INFO=28 and per-endpoint max `7/8`.

**Runtime-only alternate**: an ad-hoc gate that should be run when its mode is relevant, but that does not have a committed reviewer baseline file.
The round 9 replace-family alternates are runtime-only checks today.
