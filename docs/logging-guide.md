# Lumina Studio Logging Guide / 日志使用指南

> Operator and contributor guide for the structured logging system shipped with `log-governance-v2`. English first, 中文 second. Both halves are kept in sync; if you change one, change the other.

---

## English

### TL;DR

- Logs are JSON Lines at `<repo>/logs/lumina_<timestamp>.log` by default. Override with `LUMINA_LOG_PATH=/abs/path.log`.
- Tail in another terminal: `Get-Content -Wait -Tail 50 logs/lumina_*.log` (PowerShell) or `tail -f logs/lumina_*.log` (bash).
- Search past logs: `python scripts/audit_logs.py --logs logs/ --latest 1` for an aggregate, or `Select-String / grep` for ad-hoc lookups.
- Verify the log contract in CI / pre-PR: `python scripts/log_quality_check.py --mode fast` (smoke) and `--mode full` (release).

### 1. Where logs are written

`get_logger(name)` only acquires a namespaced logger; it does not configure
handlers, change root/Uvicorn settings, or create files. Initialize logging at
the process entry point with `configure_structured_logging()`. The API app uses
`setup_file_logging()` first to select the shared file; API workers and vector
material workers attach during their process initializers. CLI tools configure
their own output in `main()`. Keep `LUMINA_LOG_PATH` and
`LUMINA_LOG_INIT_BY_PARENT=1` inherited by child processes.

The file path resolution chain (defined in `api/logger.py::_resolve_log_candidates`):

1. **`LUMINA_LOG_PATH=/abs/path.log`** — explicit override; the file (or its parent) will be created if missing. Used in worker subprocesses to inherit the parent's log file.
2. **`LUMINA_LOG_DIR=/abs/dir`** — when no explicit path; the file is `<dir>/lumina_<YYYYMMDD_HHMMSS>.log`.
3. **`<repo>/logs/lumina_<YYYYMMDD_HHMMSS>.log`** — default for local development.
4. **`<system temp>/lumina-logs/lumina_<YYYYMMDD_HHMMSS>.log`** — last-resort fallback when the repo directory is not writable.

Other relevant environment variables:

| Variable | Values | Default | Purpose |
|---|---|---|---|
| `LUMINA_LOG_PATH` | absolute path | unset | force a specific log file (also exported by main process to children) |
| `LUMINA_LOG_DIR` | absolute path | unset | parent directory for autogenerated filename |
| `LUMINA_LOG_FORMAT` | `json` / `human` / `auto` | `auto` | console rendering; file handler is always JSON |
| `LUMINA_LOG_LEVEL` | `DEBUG` / `INFO` / `WARNING` / `ERROR` / int | `INFO` | minimum severity for both handlers |
| `LUMINA_LOG_INIT_BY_PARENT` | `1` | unset | set automatically; suppresses duplicate `log_file_configured` from children |

The file handler is always JSON Lines (one JSON object per line). The console handler auto-detects: TTY → human (one line per record with key fields), pipe → JSON (machine-parseable).

### 2. Tailing live logs

While the server runs, watch the log in a second terminal:

```powershell
# PowerShell (Windows)
Get-Content -Wait -Tail 50 logs/lumina_*.log
```

```bash
# bash / WSL / Linux
tail -f logs/lumina_*.log
```

To filter for a specific event type live (e.g. only generation-completion events):

```powershell
Get-Content -Wait -Tail 0 logs/lumina_*.log | Select-String 'converter_generate_timing'
```

```bash
tail -f logs/lumina_*.log | grep -F 'converter_generate_timing'
```

To pretty-print structured fields, pipe into `jq` (if installed):

```bash
tail -f logs/lumina_*.log | jq -r 'select(.event=="converter_generate_timing") | "\(.timestamp)  \(.duration_ms)ms  \(.session_id)"'
```

### 3. Searching past logs

JSON Lines is grep-friendly. Useful patterns:

```powershell
# All events for a specific session_id
Select-String -Path logs/lumina_*.log -Pattern '"session_id":"abc123"' -Encoding UTF8

# All errors with their type (case-insensitive substring)
Select-String -Path logs/lumina_*.log -Pattern '"level":"ERROR"' -Encoding UTF8 | ForEach-Object { ($_.Line | ConvertFrom-Json).error_type }

# Slowest preview calls (top 10 by duration_ms)
Select-String -Path logs/lumina_*.log -Pattern 'converter_preview_timing' -Encoding UTF8 |
    ForEach-Object { ($_.Line | ConvertFrom-Json) } |
    Sort-Object duration_ms -Descending |
    Select-Object -First 10 | Format-Table timestamp, duration_ms, session_id
```

```bash
# Same with jq
jq -c 'select(.event=="converter_preview_timing")' logs/lumina_*.log | jq -s 'sort_by(-.duration_ms) | .[:10]'

# Count events by type for a given log file
jq -r '.event' logs/lumina_20260428_143000.log | sort | uniq -c | sort -rn | head -20
```

### 4. Aggregate audit (`scripts/audit_logs.py`)

`audit_logs.py` produces a JSON report summarizing event distribution, structured-line ratio, and top events. Use it to check whether a recent run looked normal.

```powershell
# Summarize the latest log file in logs/
python scripts/audit_logs.py --logs logs/ --latest 1

# Audit several specific files and write to disk
python scripts/audit_logs.py --logs logs/lumina_20260428_*.log --output progress/log_audit_recent.json --label recent

# Audit the last 5 logs (e.g. after a long debugging session)
python scripts/audit_logs.py --logs logs/ --latest 5 --label session-roundup
```

Output schema (top-level keys):

| Key | Meaning |
|---|---|
| `total_lines` / `structured_lines` | record count and how many were JSON-shaped |
| `unstructured_lines` | should normally be small; non-zero suggests bare `print()` leaking in |
| `top_events` | most frequent event names (top 20) |
| `request_completed_count` | bucket-event count; **must remain 0** in governed paths |
| `duplicate_event_count` | events emitted more than once; helps spot accidental duplicates |
| `event_counts` | full event → count map |
| `total_bytes` | combined size of audited files |

If you see `request_completed_count > 0` or `unstructured_lines` ballooning, that is a governance regression — file an issue and run `log_quality_check.py` to localize.

### 5. Quality gate (`scripts/log_quality_check.py`)

This is the pre-PR gate that prevents log governance from drifting. It runs the canonical workflow against an in-process `TestClient`, then asserts the INFO budget and event coverage.

```powershell
# Smoke gate (PR-time, ~10s): canonical 10-step workflow, fast mode
python scripts/log_quality_check.py --mode fast

# Full gate (release-time, ~30s): same workflow, full vector / extractor branches exercised
python scripts/log_quality_check.py --mode full

# Ad-hoc per-endpoint gate (e.g. only the LUT merge canary):
python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,lut_merge

# Per-color-mode regression for the replace path:
python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,replace_bw
python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,replace_8color
python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,replace_5color_ext
```

Exit codes:

- `0` — PASS (no governance violation)
- `1` — governance violation (some assertion failed; details in stderr)
- `2` — script error (configuration / environment issue, not a governance failure)

The default canonical workflow is **frozen** at INFO `14/30 fast`, `29/30 full`, per-endpoint `7/8`. **Never** weaken thresholds (`--max-info`, `--max-info-per-endpoint`) to make a failing check pass — instead, find the offending event and either consolidate or demote it to DEBUG.

Two reviewer baselines lock the canonical numbers in version control:

- `progress/log_audit_fast_reviewer.json` — fast-mode expected counts
- `progress/log_audit_full_reviewer.json` — full-mode expected counts

These files **must not** change unless the canonical workflow legitimately changes (which requires an explicit governance round, e.g. PR #112 added `extract_single_stage` to canonical).

### 6. Debug recipes

#### Recipe A — "User reports the generate flow stalled"

1. Get the user's `session_id` (frontend dev console; or look up by approximate timestamp).
2. Filter the log for that session:
   ```bash
   jq -c 'select(.session_id=="<id>")' logs/lumina_<date>.log
   ```
3. Look for the chain `converter_generate_init` → `converter_generate_timing` → `converter_glb_completed`. A missing `*_timing` or `*_completed` localizes the stall.
4. If `*_timing` is present but `*_completed` is missing, scan for an ERROR record with the same `request_id`.

#### Recipe B — "Preview is slow after the latest deploy"

1. Aggregate the last 50 preview calls:
   ```bash
   jq -c 'select(.event=="converter_preview_timing")' logs/lumina_*.log | tail -50 | jq -s 'map(.duration_ms) | {min: min, max: max, mean: (add/length)}'
   ```
2. Compare against a known-good baseline (committed in `artifacts/perf_baseline.json` if `check_perf_regression.py` is enabled).
3. If the regression is real, run `python scripts/profile_stage3.py --also-write-latest` to capture a fresh profile.

#### Recipe C — "Extractor returned 500"

1. Filter ERROR records:
   ```bash
   jq -c 'select(.level=="ERROR" and .event | startswith("extractor_"))' logs/lumina_*.log | tail -20
   ```
2. Each record carries `error_type`, `error_message`, and (where applicable) `path` and `dependency`. Use these to triage.
3. If the failure path is missing structured context, that is a logging-governance bug — the WARNING/ERROR contract requires actionable fields.

#### Recipe D — "I added an endpoint and the gate fails"

1. Run the smoke gate and read the failure: `python scripts/log_quality_check.py --mode fast 2>&1 | tail -30`.
2. Common causes:
   - INFO budget exceeded → either consolidate two `*_done` events into one or demote an intermediate trace to DEBUG.
   - Per-endpoint cap hit → your new endpoint emits more than 8 INFO records on a single call; the same fix applies.
   - WARNING/ERROR missing actionable fields → add a diagnostic field such as `error_type`, `error_message`, `path`, `dependency`, `status_code`, or `fallback_action`; correlation IDs alone are not enough.
   - Missing canary on a `TARGETS` file → see §7 below.
3. Re-run targeted: `python -m pytest tests/test_logging_exception_governance_unit.py -v` to read the exact failing assertion.

### 7. Adding a new canary (contributor checklist)

When you add a mutating endpoint to a governed router file (anything in `tests/test_logging_exception_governance_unit.py::TARGETS`), you owe the system a single success-path INFO canary. Steps:

1. **Pick an event name** of the form `<family>_<action>_done`, e.g. `lut_merge_done`, `system_save_settings_done`. Names must match the family whitelist already used in `REQUIRED_STRUCTURED_EVENTS`. Two-stage flows additionally emit `<family>_<action>_init` at the entry; long-running orchestration adds `<family>_<action>_failed` on the unhappy path.
2. **Emit at the success convergence** — the latest point where all branches have merged but before `return`. Use `get_logger(__name__).info(...)` with `extra={"event": "<name>", ...discriminators}`. Discriminators must be JSON-serializable scalars (no objects, no large arrays).
3. **Register in the whitelist**: open `tests/test_logging_exception_governance_unit.py`, add the event to the matching `<FAMILY>_STRUCTURED_EVENTS` set. The unit test will then enforce that the event is present in the structured-event inventory.
4. **Add an ad-hoc workflow step** in `scripts/log_quality_check.py`: extend `WORKFLOW_ORDER` with the new step name; add the runner branch in the `dispatch_step` function; ensure required-event assertion in `_workflow_required_event_checks`.
5. **Write an integration test** under `tests/test_<family>_canary_integration_unit.py`. The test creates a `TestClient`, calls the endpoint with a minimal valid payload, captures emitted records via `caplog`, and asserts the `*_done` event with all expected discriminators.
6. **Run all three before opening the PR**:
   ```bash
   python -m pytest tests/test_logging_exception_governance_unit.py tests/test_<family>_canary_integration_unit.py -v
   python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,<your_step>
   python scripts/log_quality_check.py --mode fast    # canonical must still pass
   ```

Do **not** modify the canonical workflow, `DEFAULT_MAX_INFO`, `DEFAULT_MAX_INFO_PER_ENDPOINT`, or the reviewer baselines. Those are governance-round changes.

### 8. Event taxonomy reference

The full inventory lives at runtime in `tests/test_logging_exception_governance_unit.py::REQUIRED_STRUCTURED_EVENTS`, the 9-way union of:

| Whitelist | Family | Where defined |
|---|---|---|
| `EXTRACTOR_STRUCTURED_EVENTS` | `api/routers/extractor.py` | extract / merge / manual-fix / preview-wb / rotate / confirm-palette |
| `CONVERTER_STRUCTURED_EVENTS` | `api/routers/converter/*` | replace / preview / generate / puzzle / cleanup branches |
| `VECTOR_STRUCTURED_EVENTS` | `api/workers/vectorizer_workers.py` + converter vector branch | vector_branch_init/done, vector_3mf_exported, etc. |
| `CALIBRATION_STRUCTURED_EVENTS` | `api/routers/calibration.py` | calibration upload / clear |
| `FIVE_COLOR_STRUCTURED_EVENTS` | `api/routers/five_color.py` | clear-cache / query / generate-swatch |
| `VECTORIZER_STRUCTURED_EVENTS` | `api/routers/vectorizer.py` | POST `/api/vectorize` |
| `LUT_STRUCTURED_EVENTS` | `api/routers/lut.py` | upload / merge / compare / details / session_info |
| `SYSTEM_STRUCTURED_EVENTS` | `api/routers/system.py` | image-preview / save-settings |
| `SLICER_STRUCTURED_EVENTS` | `api/routers/slicer.py` | launch |

For governed paths, every record at INFO is one of: a `*_init`, a `*_done`, a `*_timing`, or a startup/lifecycle event (`worker_pool_started`, `lut_presets_discovered`, `log_file_configured`). Anything else at INFO is a budget regression.

### 9. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Console shows JSON instead of human-readable | piped output or non-TTY | export `LUMINA_LOG_FORMAT=human` |
| File handler missing | `LUMINA_LOG_PATH` invalid or unwritable | check stderr for `[LOG][WARNING] File logging disabled for ...`; pick a writable path |
| Worker logs missing | child process didn't inherit env | confirm `LUMINA_LOG_PATH` and `LUMINA_LOG_INIT_BY_PARENT=1` are exported in the worker spawn site |
| `log_quality_check.py` fails with HTTP 404 / 500 | runner-side fixture mismatch with a service catalog | inspect `scripts/log_quality_check.py` for the offending step; runner-side fixture amendments precedent: PRs #112, #113, #117, #119 |
| `audit_logs.py` shows non-zero `request_completed_count` | bucket event leaked into governed code | grep for `event="request_completed"` in modified files; replace with the specific success canary |
| INFO budget hits 30/30 in `full` mode | another canary added to canonical workflow | run a governance round per `progress/round-17-onwards-master-plan.md`; do not raise the cap |

For a deeper governance reference, see `progress/governance-roadmap.md` (v2 final coverage map) and the AGENTS.md "Logging Governance" section.

## 中文

### 一句话要点

- 日志默认写在 `<repo>/logs/lumina_<时间戳>.log`, 用 JSON Lines 格式. 想换路径设 `LUMINA_LOG_PATH=/abs/path.log`.
- 实时跟看: `Get-Content -Wait -Tail 50 logs/lumina_*.log` (PowerShell) 或 `tail -f logs/lumina_*.log` (bash).
- 查历史: `python scripts/audit_logs.py --logs logs/ --latest 1` 出汇总, 或 `Select-String / grep` 即兴查找.
- PR / 发版前过 gate: `python scripts/log_quality_check.py --mode fast` (smoke) 与 `--mode full` (发版).

### 1. 日志写到哪

`get_logger(name)` 只获取命名空间下的 logger，不配置 handler、不改变
root/Uvicorn 设置，也不创建文件。进程入口负责调用
`configure_structured_logging()`。API app 先用 `setup_file_logging()`
确定共享日志文件；API worker 和矢量材料 worker 在各自的进程初始化器中
接入日志。CLI 在 `main()` 中配置输出。子进程继续继承 `LUMINA_LOG_PATH`
和 `LUMINA_LOG_INIT_BY_PARENT=1`。

文件路径解析链 (实现在 `api/logger.py::_resolve_log_candidates`):

1. **`LUMINA_LOG_PATH=/abs/path.log`** — 显式覆盖; 文件 (及父目录) 不存在会自动创建. Worker 子进程靠继承这个变量复用主进程日志文件.
2. **`LUMINA_LOG_DIR=/abs/dir`** — 没有显式 path 时使用; 文件名是 `<dir>/lumina_<YYYYMMDD_HHMMSS>.log`.
3. **`<repo>/logs/lumina_<YYYYMMDD_HHMMSS>.log`** — 本地开发默认.
4. **`<系统 temp>/lumina-logs/lumina_<YYYYMMDD_HHMMSS>.log`** — 仓库目录不可写时的兜底.

相关环境变量:

| 变量 | 取值 | 默认 | 用途 |
|---|---|---|---|
| `LUMINA_LOG_PATH` | 绝对路径 | 未设 | 强制指定日志文件 (主进程也会导给子进程) |
| `LUMINA_LOG_DIR` | 绝对路径 | 未设 | 自动生成文件名时的父目录 |
| `LUMINA_LOG_FORMAT` | `json` / `human` / `auto` | `auto` | 控制台渲染; 文件 handler 永远 JSON |
| `LUMINA_LOG_LEVEL` | `DEBUG` / `INFO` / `WARNING` / `ERROR` / 数字 | `INFO` | 两个 handler 共同的最低级别 |
| `LUMINA_LOG_INIT_BY_PARENT` | `1` | 未设 | 自动设置; 抑制 worker 重复发 `log_file_configured` |

文件 handler 永远是 JSON Lines (一行一个 JSON 对象). 控制台 handler 自动判定: TTY → human (一行一条带主要字段), 管道 → JSON (机器可解析).

### 3. 查历史日志

JSON Lines 对 grep 友好. 常用模式:

```powershell
# 某个 session_id 的全部事件
Select-String -Path logs/lumina_*.log -Pattern '"session_id":"abc123"' -Encoding UTF8

# 所有 ERROR 及其 error_type
Select-String -Path logs/lumina_*.log -Pattern '"level":"ERROR"' -Encoding UTF8 | ForEach-Object { ($_.Line | ConvertFrom-Json).error_type }

# 最慢的 10 次 preview 调用
Select-String -Path logs/lumina_*.log -Pattern 'converter_preview_timing' -Encoding UTF8 |
    ForEach-Object { ($_.Line | ConvertFrom-Json) } |
    Sort-Object duration_ms -Descending |
    Select-Object -First 10 | Format-Table timestamp, duration_ms, session_id
```

```bash
# 同样的事用 jq 写
jq -c 'select(.event=="converter_preview_timing")' logs/lumina_*.log | jq -s 'sort_by(-.duration_ms) | .[:10]'

# 某个日志文件按事件类型计数
jq -r '.event' logs/lumina_20260428_143000.log | sort | uniq -c | sort -rn | head -20
```

### 4. 汇总审计 (`scripts/audit_logs.py`)

`audit_logs.py` 输出 JSON 报告, 含事件分布、结构化行占比、Top 事件. 用来快速判断某次运行是否正常.

```powershell
# 汇总 logs/ 里最新的 1 个文件
python scripts/audit_logs.py --logs logs/ --latest 1

# 审计指定的几个文件并落盘
python scripts/audit_logs.py --logs logs/lumina_20260428_*.log --output progress/log_audit_recent.json --label recent

# 审计最近 5 个文件 (例如长 debug 会话后)
python scripts/audit_logs.py --logs logs/ --latest 5 --label session-roundup
```

输出 schema 顶层字段:

| 字段 | 含义 |
|---|---|
| `total_lines` / `structured_lines` | 总记录数 + 有 JSON 形态的数量 |
| `unstructured_lines` | 应该很小; 不为零暗示有裸 `print()` 漏出 |
| `top_events` | 最频繁的事件名 (Top 20) |
| `request_completed_count` | 桶事件计数; 治理路径**必须为 0** |
| `duplicate_event_count` | 出现多次的事件; 用来排查意外重复 |
| `event_counts` | 完整 event → count 映射 |
| `total_bytes` | 审计文件总字节数 |

如果 `request_completed_count > 0` 或 `unstructured_lines` 暴涨, 这是治理回归 — 提 issue 并跑 `log_quality_check.py` 定位.

### 5. 质量门 (`scripts/log_quality_check.py`)

这是 PR 前的把关脚本, 防止日志治理慢慢退化. 它在内存里跑 canonical workflow (用 `TestClient`), 然后断言 INFO 预算和事件覆盖.

```powershell
# Smoke gate (PR 前, 约 10 秒): canonical 10 步, fast 模式
python scripts/log_quality_check.py --mode fast

# Full gate (发版前, 约 30 秒): 同样 workflow, full 模式跑完整 vector / extractor 分支
python scripts/log_quality_check.py --mode full

# 即兴单端点 gate (例如只测 LUT merge canary):
python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,lut_merge

# 替换路径的颜色模式回归:
python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,replace_bw
python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,replace_8color
python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,replace_5color_ext
```

退出码:

- `0` — PASS (无违规)
- `1` — 治理违规 (有断言失败; stderr 有详情)
- `2` — 脚本错误 (配置 / 环境问题, 不算治理违规)

默认 canonical workflow **冻结** 在 INFO `14/30 fast`、`29/30 full`、单端点 `7/8`. **永远不要**为了让失败检查通过而调阈值 (`--max-info`、`--max-info-per-endpoint`) — 应去找触发的事件, 合并或降级到 DEBUG.

两份 reviewer baseline 把 canonical 数字锁进版本库:

- `progress/log_audit_fast_reviewer.json` — fast 模式预期计数
- `progress/log_audit_full_reviewer.json` — full 模式预期计数

这两份**不允许变**, 除非 canonical workflow 真有合法变更 (这是治理回合事项, 例如 PR #112 把 `extract_single_stage` 加进 canonical).

### 6. Debug 套路

#### 套路 A — "用户报 generate 流程卡住"

1. 拿到该用户的 `session_id` (前端开发者控制台; 或按时间近似查).
2. 过滤该 session:
   ```bash
   jq -c 'select(.session_id=="<id>")' logs/lumina_<日期>.log
   ```
3. 找链路 `converter_generate_init` → `converter_generate_timing` → `converter_glb_completed`. 缺哪一段就是哪段卡了.
4. 如果有 `*_timing` 但缺 `*_completed`, 扫同 `request_id` 的 ERROR 记录.

#### 套路 B — "上线后 preview 变慢了"

1. 汇总最近 50 次 preview:
   ```bash
   jq -c 'select(.event=="converter_preview_timing")' logs/lumina_*.log | tail -50 | jq -s 'map(.duration_ms) | {min: min, max: max, mean: (add/length)}'
   ```
2. 对比一个公认 OK 的 baseline (启用了 `check_perf_regression.py` 的话, 在 `artifacts/perf_baseline.json`).
3. 回归是真的, 跑 `python scripts/profile_stage3.py --also-write-latest` 抓最新 profile.

#### 套路 C — "Extractor 返回 500"

1. 过滤 ERROR 记录:
   ```bash
   jq -c 'select(.level=="ERROR" and .event | startswith("extractor_"))' logs/lumina_*.log | tail -20
   ```
2. 每条记录都带 `error_type`、`error_message`, 必要时还有 `path`、`dependency`. 用这些信息分诊.
3. 如果失败路径**没**结构化字段, 这本身是治理 bug — WARNING/ERROR 必须带可执行字段.

#### 套路 D — "我加了一个端点, gate 挂了"

1. 跑 smoke gate 看输出: `python scripts/log_quality_check.py --mode fast 2>&1 | tail -30`.
2. 常见原因:
   - INFO 预算超了 → 合并两个 `*_done` 或把中间 trace 降到 DEBUG.
   - 单端点上限 8 触顶 → 你的新端点单次调用发了 > 8 条 INFO, 同样的修法.
   - `TARGETS` 文件没加 canary → 看下面第 7 节.
3. 跑 targeted: `python -m pytest tests/test_logging_exception_governance_unit.py -v` 看具体是哪条断言.

### 7. 新增 canary (贡献者 checklist)

当你给某个治理 router 文件 (`tests/test_logging_exception_governance_unit.py::TARGETS` 列出的任一个) 新增 mutating 端点时, 你欠系统一条成功路径的 INFO canary. 步骤:

1. **取事件名** 用 `<family>_<action>_done` 形式, 例如 `lut_merge_done`、`system_save_settings_done`. 名字必须匹配 `REQUIRED_STRUCTURED_EVENTS` 里已有的家族 whitelist. Two-stage 流程额外在入口发 `<family>_<action>_init`; 长流程在异常分支发 `<family>_<action>_failed`.
2. **在成功收敛点发** — 所有分支已合并、`return` 之前的最晚一处. 用 `get_logger(__name__).info(...)` 配 `extra={"event": "<name>", ...discriminators}`. Discriminators 必须是 JSON 可序列化的标量 (不要塞对象、不要塞大数组).
3. **登记 whitelist**: 打开 `tests/test_logging_exception_governance_unit.py`, 把事件加进对应的 `<FAMILY>_STRUCTURED_EVENTS` 集合. 单元测试随后会断言事件出现在结构化事件清单里.
4. **加 ad-hoc workflow step** 在 `scripts/log_quality_check.py`: 把新步名加进 `WORKFLOW_ORDER`; 在 `dispatch_step` 里加 runner 分支; 在 `_workflow_required_event_checks` 里加必需事件断言.
5. **写集成测试** 在 `tests/test_<family>_canary_integration_unit.py`. 测试创建 `TestClient`, 用最小合法 payload 调端点, 通过 `caplog` 抓发出的记录, 断言 `*_done` 事件及全部预期 discriminator.
6. **PR 前三个都跑一遍**:
   ```bash
   python -m pytest tests/test_logging_exception_governance_unit.py tests/test_<family>_canary_integration_unit.py -v
   python scripts/log_quality_check.py --mode fast --workflow startup,lut_list,lut_colors,preview,generate,<your_step>
   python scripts/log_quality_check.py --mode fast    # canonical 仍要过
   ```

**不要**改 canonical workflow、`DEFAULT_MAX_INFO`、`DEFAULT_MAX_INFO_PER_ENDPOINT` 或 reviewer baseline. 这些是治理回合的事.

### 8. 事件分类参考

完整清单运行时存在 `tests/test_logging_exception_governance_unit.py::REQUIRED_STRUCTURED_EVENTS`, 它是 9 个集合的联合:

| Whitelist | 家族 | 出处 |
|---|---|---|
| `EXTRACTOR_STRUCTURED_EVENTS` | `api/routers/extractor.py` | extract / merge / manual-fix / preview-wb / rotate / confirm-palette |
| `CONVERTER_STRUCTURED_EVENTS` | `api/routers/converter/*` | replace / preview / generate / puzzle / cleanup 各分支 |
| `VECTOR_STRUCTURED_EVENTS` | `api/workers/vectorizer_workers.py` + converter vector 分支 | vector_branch_init/done, vector_3mf_exported 等 |
| `CALIBRATION_STRUCTURED_EVENTS` | `api/routers/calibration.py` | calibration upload / clear |
| `FIVE_COLOR_STRUCTURED_EVENTS` | `api/routers/five_color.py` | clear-cache / query / generate-swatch |
| `VECTORIZER_STRUCTURED_EVENTS` | `api/routers/vectorizer.py` | POST `/api/vectorize` |
| `LUT_STRUCTURED_EVENTS` | `api/routers/lut.py` | upload / merge / compare / details / session_info |
| `SYSTEM_STRUCTURED_EVENTS` | `api/routers/system.py` | image-preview / save-settings |
| `SLICER_STRUCTURED_EVENTS` | `api/routers/slicer.py` | launch |

治理路径下, 每条 INFO 必须是: `*_init`、`*_done`、`*_timing`、或启动/生命周期事件 (`worker_pool_started`、`lut_presets_discovered`、`log_file_configured`) 之一. INFO 出现其他东西就是预算回归.

### 9. 故障排查

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 控制台显示 JSON 而非可读形式 | 输出被管道接走或非 TTY | export `LUMINA_LOG_FORMAT=human` |
| 文件 handler 缺失 | `LUMINA_LOG_PATH` 不合法或不可写 | 看 stderr 有没有 `[LOG][WARNING] File logging disabled for ...`; 换可写路径 |
| Worker 日志缺失 | 子进程没继承到环境变量 | 确认 worker spawn 处导出了 `LUMINA_LOG_PATH` 与 `LUMINA_LOG_INIT_BY_PARENT=1` |
| `log_quality_check.py` 报 HTTP 404 / 500 | runner 端 fixture 与某服务 catalog 不匹配 | 看 `scripts/log_quality_check.py` 的相关 step; runner-side fixture 修复先例: PRs #112、#113、#117、#119 |
| `audit_logs.py` 的 `request_completed_count` 不为 0 | 桶事件漏进治理代码 | 在改动文件里 grep `event="request_completed"`; 替换成具体的成功 canary |
| Full 模式 INFO 触顶 30/30 | 有人把新 canary 加进了 canonical workflow | 按 `progress/round-17-onwards-master-plan.md` 走治理回合; 不要抬上限 |

需要更深入的治理参考, 看 `progress/governance-roadmap.md` (v2 final 覆盖图) 和 AGENTS.md "Logging Governance" 节.
