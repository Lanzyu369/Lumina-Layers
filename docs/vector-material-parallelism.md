# 材质建模并行与内存写盘验证

日期：2026-09-14。基础提交：`2e5d94bb2579d5428567df73386661797c05dff6`。
分支：`Min/fix/vector-material-parallelism`。

## 行为

独立材质使用可移植的 spawn 进程并行计算，沿用现有闭壳体几何算法。
进程数共同受实际 CPU 容量、其他任务需求、独立材质数、工作量及内存预算约束，
没有 AMD/Intel 型号白名单，也没有针对 9800X3D 固定进程数。
Linux 容器 CPU 配额和现有 Apple 性能核心策略继续生效。
小任务不承担进程启动成本。

进程之间只传标量和私有文件路径。材质次序、ID、物理网格和异常传播保持不变。
独立监控进程在父任务异常退出后清理计算进程及传输文件；普通错误会先停止同批计算，
再释放临时目录。Windows 子进程验证包含“主程序→任务进程→材质进程”。

新增片层网格自动写盘：内存充足时直接累计；内存紧张时逐片写入临时缓冲文件，
最后通过可写磁盘映射组成完整数组。该路径不会降低精度、减少面数或改变材质。
临时缓冲的寿命由操作系统文件句柄和数组映射引用管理，关闭构建上下文不会使返回数组失效。
这减少了同时保留所有片层及最终合并副本造成的峰值。

这不是完整的全流程磁盘化：SVG 解析、单个几何操作、坐标变换和导出仍需要工作内存。
磁盘映射也会使用可回收的文件缓存，不代表零 RAM。现有最低安全内存检查没有被删除；
不能据此承诺任意复杂模型都能在任意小内存设备上生成。

## 可重复的材质阶段对比

同一份 12 材质片层输入；每个配置启动三个独立 Python 进程，取第 2/3 次的耗时中位数。
统计整组进程的 RSS 峰值，包含监控及计算子进程。BLAS/OpenMP 使用一个线程，
避免各子进程再创建计算线程池。以下是材质阶段，不是整个应用的加速倍数。

| 设备 | 配置 | 实际材质进程 | 热运行耗时 | 三次最大进程组 RSS |
|---|---|---:|---:|---:|
| Windows / 9800X3D | 串行 | 0 | 25.360 s | 242.0 MiB |
| Windows / 9800X3D | 2 | 2 | 18.344 s | 582.3 MiB |
| Windows / 9800X3D | 4 | 4 | 11.173 s | 812.1 MiB |
| Windows / 9800X3D | 自动 | 12 | 9.458 s | 1752.1 MiB |
| Linux / 13900H | 串行 | 0 | 31.685 s | 266.8 MiB |
| Linux / 13900H | 2 | 2 | 17.720 s | 641.3 MiB |
| Linux / 13900H | 4 | 4 | 9.706 s | 919.2 MiB |
| Linux / 13900H | 自动 | 8 | 7.152 s | 1439.1 MiB |

Linux 为独立、无网络、无生产数据挂载的临时容器，CPU 配额 8，内存 8 GiB。
物理服务器为 13900H、14 核/20 线程、32 GiB；检测结果确实采用 cgroup 配额 8。
没有重启或更新在线服务。Windows 是 Python 3.12.7 / NumPy 2.3.2 / Trimesh 4.11.2；
Linux 是 Python 3.13.14 / NumPy 2.5.2 / Trimesh 5.1.0。
每个平台内的全部配置都与自己的串行顶点/面数组哈希完全一致。
两个平台依赖版本不同，跨平台原始哈希不相同，不把它们作为同一字节级基准。

## 完整导出和写盘

- Windows：原始串行单次完整导出 47.436 s；最终支持写盘的自动并行版本单次 27.917 s，
  通过外部串行模型语义校验。之前连续三次自动运行为 28.553 / 20.529 / 20.486 s；
  后两次有进程内缓存，不拿它们直接除以前面的单次基线来宣称加速倍数。
- Linux：串行单次 54.679 s，自动单次 25.298 s；完整模型、材质和导出语义与串行一致。
  整体自动模式也启用了既有其他阶段并行，不能把所有收益都归给新增材质进程。
- Linux 2 GiB 容器强制片层写盘：完整导出成功，54.435 s，峰值 486.81 MiB，
  与本平台串行的外部语义校验一致。强制开关仅存在于本地测试脚本。
- 512 万三角面的独立累计测试：RAM 路径峰值 451.57 MiB，磁盘路径 257.39 MiB；
  两者完整数组哈希相同。耗时 0.178 / 0.256 s，只证明该累计阶段的内存取舍。

复杂 `benchmark.svg` 在基础版本最新原生解析路径上存在已复现的 GEOS TopologyException。
上述完整复杂图对比显式使用现有整文档解析回退，并在报告记录原因，几何内核仍是当前闭壳体内核。
Windows 的小型 `1.svg` 另行验证默认路径；Linux 镜像缺少新的原生解析包，默认使用既有回退。
本改动不声称修复该独立解析问题，也不修改生产解析选择。

## 参考设计

采用分块、写盘和动态并行的分层策略，而不是内存不足立即拒绝全部工作：

- [Dask 的写盘、暂停新任务及最终保护](https://distributed.dask.org/en/stable/worker-memory.html)
- [GDAL 按内存预算拆分处理区域](https://gdal.org/en/stable/programs/gdalwarp.html)
- [NumPy 大数组的磁盘映射](https://numpy.org/doc/stable/user/how-to-io.html)

当前实现未引入 Dask 或 GDAL 作为新依赖；参考其资源管理方式，使用现有 NumPy 和标准库实现。
