# Windows 白屏：入口资源类型修复

## 已确认的直接原因

2026-09-23 返回的两份隔离诊断报告均记录：已发布包入口 JS 为 HTTP 200，字节匹配包内文件，但 Content-Type 是 text/plain，Electron 明确拒绝执行模块；rootChildren=0，设置和转换入口未生成。两份报告的用户身份需由维护者确认，不根据匿名文件名推断是两个独立用户。

故障包为 2.0.0-beta.20260922055719，源码 eb1c5ffb01eb8f979403f44ad6ae16db1ed142aa，ZIP SHA-256 为 8b5a8435e9165558f1fe8bad964d0d5605987dba820b2e65c08eaf59abacf628。原始用户资料和日志不提交到仓库。

Windows 上 Python MIME 推断可以受注册表文件类型关联影响；具体哪个软件或注册表值改变了用户映射尚未核查，也不需要通过改用户注册表来修复应用自己的响应类型。

## 最小改动

只在 FastAPI 的前端静态资源服务中明确 JS/MJS、CSS、HTML 的媒体类型。其他资源沿用原 StaticFiles/FileResponse 行为，全局 mimetypes、操作系统关联、浏览器安全设置均不改变。没有修改启动器、增量或支付。

已知入口资源的 ETag 包含媒体类型，避免文件内容没变时错误返回 304、继承旧 Content-Type。时间戳本身无法区分旧响应类型，因此这些资源仅凭匹配 ETag 返回 304；其余资源保留框架原有条件缓存处理。路径检查、HEAD、Range 及新 ETag 的缓存复用保留。

## 构建与缓存注意事项

必须按正常本体构建流程同时携带更新后的后端和前端。更新说明已加入前端；本轮构建产生新的内容哈希入口文件名。不要只热替换后端并保留旧 index.html/入口文件名，然后宣称所有已有缓存已恢复。

实际 Chromium 对照显示：同 URL 的旧 JS 可能仍被直接从磁盘缓存读取，服务端此时无请求可响应，ETag 无法主动清除此类缓存。使用正常重建后的 index.html 和新哈希资源后，同一浏览器会话、不清空缓存即可恢复。没有增加全局缓存清理或自动刷新机制。

## 验证

- 错误 MIME 进程映射下，原代码 10 项新增测试失败；固定类型后通过。
- 缓存补充测试在初稿实际捕获 304 保留旧类型，最终修正通过；新增用例同时检查正常 304、HEAD、Range、原字节、PNG、404 和路径逃逸。
- 静态资源、App、桌面 origin/构建契约合计 50 项 pytest 通过。
- 用真实 HTTP 服务执行原/新静态服务函数，提供同一发行 JS，在 Electron 35.7.5 中：原实现 MIME 拒绝、root=0；修复后 root=1，主界面控件生成。仅在测试进程改变 MIME 映射，不修改注册表，不使用 Playwright 响应拦截。
- 同 URL 已有错误磁盘缓存 + 完整重建资源的升级对照通过，无需清缓存。
- 复用现有发行 Electron 外壳、素材和构建工具，仅重新构建 Windows 后端及前端，隔离候选可初始化、切换设置、导入 PNG。
- 候选冻结后端通过已有检查器的一条传统 LUT 图片预览/GLB/3MF 流程，实际校验有效几何；未扩成七项全矩阵。
- TypeScript 检查、前端构建、公告相关 Vitest 包装入口（34 项）、日志 fast 门禁通过。
- 最终候选同资料重启、设置页切换及返回通过，重新校验图片预览/GLB/3MF 有效几何通过；经测试进程程序化确认原退出对话框后走原 app.quit 路径，退出码 0，后端回收。不是客户手工复测。

## 边界

这是客户直接原因已确认、内部修复已验证的候选；故障用户使用修复包的现场复测仍待完成。ready 同时为真而 root 为空的误报也已确认，但本次不扩展启动握手。未升级 Electron、禁用 GPU、改驱动、清资料或正式发布。
