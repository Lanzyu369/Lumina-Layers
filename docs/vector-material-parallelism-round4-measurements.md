# 第四轮（性能线）测量记录：两条用户流程的阶段耗时与设备矩阵

2026-09-15；`Min/perf/vector-material-parallelism`，基线 `dev-refactor` (`2e5d94bb`)。
本文件只记录耗时与资源数据；F3 的容器内存改动见
`docs/vector-material-parallelism-round4.md`，SVG 诊断不在本分支。

## 方法

要回答的是**等待时间**，不是 CPU 占用率。两条用户流程分开测：

1. 上传 → 上色/预览（`phase=preview`）；
2. 点击生成 → 3MF（`phase=generate`）。

两条测量路线，两个都不做任何“强制原生”处理：

- **独立进程内路线**：`scripts/profile_converter_multicore.py`，同一进程内跑
  N 轮，第 1 轮为冷启动，其余取中位数作热值；
- **真实进程池路线**：`WorkerPoolManager.submit_timed(worker_generate_model,
  …)`，即产品自己的入口，能分别看到 `queue_wait_s` 与 `worker_execution_s`。

对比口径：相同样本、相同后端、相同物理尺寸与喷嘴/层高/耗材设置——目标宽度
299 mm、12 材质。冷启动与热运行分开；不与缓存命中的新版本比未缓存的基线。
跨版本对比一律使用**交替 A/B**（同一时间窗内 baseline 与 perf 轮流各跑一次），
因为本轮先做的非交替对比出现过会话级漂移：同一份基线代码在两个不同时段相差
10%，交替后消失。

语义闸门：每个条目都带 `reference_sha256`（尺寸、材质 ID/顺序、层段、必要的
体积/面积与洞/缺失/闭合检查），**只有与基线参考报告逐例一致才计入下表**。
所有 perf 条目 `reference_match: true`。

## 两条流程分别改善多少

**流程 1（上传 → 上色/预览）：无改善，且本分支不改变这条路径。** 预览在材质
阶段之前结束，没有可并行的材质工作。交替 A/B 显示与基线持平（总耗时中位
3.66 s vs 3.57 s，阶段级差异在 ±0.05 s 内）。

**流程 2（点击生成 → 3MF）：**

- 材质阶段真正进场时：13.99 → **9.83 s（−29.7%）**，其中材质阶段
  9.31 → **4.93 s（−47%）**；
- 独立进程内路线：热 13.51 → **11.66 s（−13.7%）**，冷 13.98 → **11.61 s（−17.0%）**；
- 产品自带预留、3.8 MB 文档：13.31 → 12.90 s，**没有实质改善**，原因是材质
  阶段未被准入（见上）；
- 小/中档：无变化，1 个 worker、`insufficient_work_units`——小任务不承担进程
  启动成本，这是既有设计；
- 强制串行：与基线持平（交替 A/B）；
- 超大文档：两棵树都拒绝。

## 自动模式在不同设备上怎么分配

依次收窄，每一步都可在计时字段里看到：

1. **有效 CPU**：CPU 亲和性 → cgroup v2 CPU 配额（向上取整）→ Apple 性能核心
   策略；无法确认时为 `unknown` 且不放大；
2. **外层需求**：读取活跃负载快照（`demand.json`）得到同时运行的任务数；快照
   不可用时回退到配置容量（`default_outer_workers = min(有效 CPU, 4)`），并在
   `demand_snapshot_fallback` 标记；
3. **CPU 公平份额**：`有效 CPU // 外层需求`；
4. **工作量上限**：独立工作项数、细粒度有效工作量、阶段硬上限；
5. **内存上限**：容器/宿主机可用内存扣除预留后除以单 worker 估算；
6. **租约准入**：`free = 有效 CPU − 其他任务已预留 worker`，只授予剩余部分，
   剩余为 0 时授予 0（在已占用的进程内串行构建）。

同一台 16 逻辑 CPU 设备上的实际取值：独立路线单任务
`outer_demand=4`（快照缺失回退）→ `cpu_fair_share=4`，取 4 个 worker；
进程池单任务发布 `outer_demand=1` → 公平份额 16，外层计划由工作量限到 5，
材质阶段再由材质预算/租约取 10（显式预留时）或 1（产品默认预留时）。
**没有把某个固定值（例如 4）当成机器容量**，也不会把独占机器固定压到 1/4。

※ 基线树上没有 `get_owned_memory_report`，采样器回退到 `psutil`，这些行里
`container_source` 记为 `unavailable`，**进程组口径与 perf 行不完全相同**
（子进程的计入方式更弱），因此不把基线/perf 的进程组峰值直接相减当作净增。

如实记录代价：在口径一致的对比里（12 GiB 单任务，强制串行 542 MiB → 自动
1738 MiB），并行路径把任务进程组峰值抬高了约 1.2 GiB。材质网格在父进程内存中
累积的部分照旧，并没有因为子进程能写盘就变成磁盘化流水线——这是用内存换等待
时间，不是“免费加速”。自动（10 worker）比固定 4（1021 MiB）多付约 0.7 GiB，
换回来的是材质阶段 4.93 s vs 4.69 s（固定 4 反而略快），所以本设备上“自动”
并不总是最优；保留固定档就是为了这种情况。

## 语义与工艺参数保持

- 独立路线每个 perf 条目 `reference_match: true`，`reference_sha256` 与基线
  参考逐例一致（尺寸/材质 ID 与顺序/层段/必要体积面积与洞、缺失、闭合检查）；
- 进程池路线 3MF **文件字节数逐次一致（31 917 737）**；逐条目 CRC 对比显示
  19 个条目中只有 `Metadata/model_settings.config` 不同，且差异只是内嵌的带
  时间戳输出文件名（`…_010808.3mf` vs `…_010835.3mf`），几何与材质载荷字节
  完全相同。整包 sha256 因该时间戳不同，不作为字节级相等证据；
- 本轮没有改动颜色算法、耗材定义、打印机设置、几何容差或喷嘴参数。

## 设备矩阵

| 设备/环境 | 结论 |
|---|---|
| Windows 桌面，16 逻辑 CPU / 61.7 GiB | **实测**：本文件 A、B 两节全部数据 |
| WSL Linux（cgroup v2，隔离） | **容量探测实测**（真实 cgroup 文件）；**转换流程未测**——该发行版缺 numpy/shapely/trimesh/psutil 与原生扩展，本轮不安装 |
| 受限容器（生产 8 GiB 配额容器） | **未测**：本轮不启动/重启既有服务，也不新建付费机器 |
| Apple Silicon 设备 | **未测**：本会话无该设备访问权 |
| 低配设备（1/2/4 CPU） | **参数化单测覆盖**，非实机实测 |
| 500 GiB 级磁盘/内存压力 | 只做了有界探测，不做耗尽性测试 |

低配覆盖用例：`test_small_device_admission_keeps_the_sum_inside_capacity`
（容量 1/2/4 × 已有 0/1 个任务），断言到达任务的授予量恰为剩余量、0 是合法授予、
发布表里的 worker 总和不超过容量；另有既有的
`cpus ∈ {1,2,4,10,16,20,32}` × `outer_demand ∈ {1,4}` 计划矩阵与容器内存用例。
模拟的 CPU 数量不作为“在某台真实设备上测过”的证据。

- 本分支的 44 个失败**全部**也是基线的失败（集合是基线的真子集），

  - 3 个由导入期模块替换缺陷的修复解决
