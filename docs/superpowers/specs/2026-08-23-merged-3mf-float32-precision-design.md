# 合并 3MF 的 float32 无损写出设计

## 结论

合并 3MF 导出必须与普通 3MF 导出采用相同的 float32 无损十进制写出契约：
顶点坐标使用 9 位有效数字。此次只修复 Lumina 对 `neroued_3mf` 安全默认值的
错误覆盖，不修改几何算法、不引入 fp64 或定点坐标，也不把上游库改动混入本
次提交。

## 已确认事实

- `neroued_3mf` 的网格顶点类型是 `Vec3f`，Python 的 float64 NumPy 数组在
  `Mesh.from_arrays()` 边界转换为 float32。
- 当前安装的 `neroued-3mf 0.3.0` 中，`WriteOptions().vertex_precision`
  默认值为 9；上游源码也把 9 定义为完整 float32 精度。
- 普通写出器显式使用 `vertex_precision = 9`。
- 合并写出器显式使用 `vertex_precision = 6`，覆盖了上游安全默认值。
- 在 200 mm 坐标附近，`200.0f` 与它的下一个可表示 float32 值会被 6 位有效
  数字写成同一 XML 坐标；这会使原本不同的顶点重合，并可能产生退化三角形。
- 二进制 STL 同样以 float32 存储顶点，且不保存共享顶点拓扑、多材料和切片
  工程信息，因此不是替代方案。

## 方案比较

### 方案 A：合并写出显式使用 9 位有效数字（采用）

把合并写出器的 `vertex_precision` 从 6 改为 9，并用真实解包后的 3MF XML
验证相邻 float32 顶点仍然不同。普通和合并写出器继续明确声明同一契约。

该方案改动最小，不依赖新版本上游库，也不会改变网格、材料、对象结构和切片
配置。最终 ZIP 体积与写入时间必须通过同输入的 6/9 位对照实测，而不是推测。

### 方案 B：删除覆盖并依赖库默认值（不采用）

当前上游默认值确实是 9，但 Lumina 的文件正确性不应只依赖可升级依赖的隐式
默认值。显式配置加回归测试能让依赖升级时更容易发现契约变化。

### 方案 C：改用 fp64、定点坐标或 STEP/STL（不采用）

这些方案会改变几何表示、依赖和切片兼容边界，却不能改变 Bambu Studio 与 Orca
最终使用 float 网格的事实。它们扩大风险，且不能为本次精度覆盖错误提供更直接
的修复。

## 行为与范围

修改只发生在合并导出器构造 `neroued_3mf.WriteOptions` 的位置。输入网格仍在
进入库时转换为 float32，9 位有效数字只保证这个 float32 值写入 XML 并再次读
取时不发生第二次精度损失。

不修改：

- 普通/矢量几何生成与拓扑修复；
- 合并排版、擦料塔位置、材料槽位和厂商元数据；
- 3MF 单位、对象结构、压缩方式和文件生命周期；
- `neroued_3mf` 依赖版本和上游源码。

## 自动验证

1. 构造 200 mm 附近相邻的两个真实 float32 值。
2. 先用普通写出器生成源 3MF，再由合并写出器重写 per-item model。
3. 解压两份 3MF，解析 `3D/Objects/object_1.model`。
4. 断言源文件和合并文件的顶点坐标都保持唯一，且每个三角面的三个坐标不同。
5. 运行全部合并写出集成测试以及直接相关的普通写出、拼图和批量测试。
6. 对同一简单模型和代表性复杂模型分别以 6/9 位写出，记录最终压缩包大小和
   写入时间；9 位输出不得出现异常级体积或性能增长。
7. 对最终 3MF 做 XML 拓扑检查，并在可用的 Bambu Studio/OrcaSlicer CLI 中
   完成加载或切片验证。

## 可选上游改进

`neroued_3mf` 当前行为已经正确，因此上游 PR 不是本次修复的依赖。后续可独立
评估：当调用者选择完整 float32 精度时，使用 C++ `std::to_chars` 的最短可往返
重载，减少 XML 字符数；1–8 位继续作为明确的有损选择。该优化应有跨平台位级
往返测试和压缩后体积基准，并单独提交给上游。
